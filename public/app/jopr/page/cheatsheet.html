Design Systems

Twitter

Here is how the generic Master Skeleton directly maps to the classic "Design Twitter / X" prompt.

A Twitter clone boils down to two core operations: Post a Tweet (Write) and View Home Timeline (Read). Because reads outnumber writes by 100:1 or more, the architecture is tailored around fast timeline delivery.

The Architecture Diagram

Mapping the 10 Universal Suspects to Twitter

Component Standard Role Twitter-Specific Implementation
1. CDN Edge cache Serves user avatars, tweet media (PNG, JPEG, MP4 chunks), and pre-rendered public tweets.
2. Load Balancer Traffic distribution Terminates TLS, round-robins traffic across stateless API pods.
3. API Gateway Auth & Perimeter guard Authenticates JWT/session, enforces rate limits (e.g., standard accounts capped at 100 tweets/hour to block spambots).
4. Tweet Service Core write compute Validates 280-char limit, assigns a 64-bit globally unique tweet_id (Snowflake ID), writes to DB, and emits an event.
5. Timeline Service Core read compute Fetches the user's pre-computed timeline from Redis in sub-10ms. If a cache miss occurs, falls back to querying the DB.
6. Primary DB Source of truth Relational DB (Postgres/MySQL) or partitioned NoSQL (DynamoDB/Cassandra). Stores tweets, user profiles, and social follow graphs.
7. Message Queue Asynchronous decoupler Kafka topic tweet-created. Decouples saving the tweet from the expensive process of notifying followers.
8. Fan-out Workers Background compute Pulls tweet-created events, queries the follow graph for the author's followers, and pushes the new tweet_id into each follower's Redis timeline.
9. Timeline Cache Read acceleration In-memory Redis cluster. Every active user has a Redis List or ZSet storing their top 800 recent tweet IDs.
10. Media Store Blob storage AWS S3 for raw media uploads (not drawn above, but referenced: clients upload media to S3 via pre-signed URLs; tweet contains the S3 URL).

The Interviewer's Favorite Deep-Dive: Fan-Out

In a Twitter interview, the interviewer almost always pushes on one specific bottleneck: The Fan-out Strategy.

1. Fan-out-on-Write (Push Model)

  • How it works: When user A posts a tweet, background workers look up A's 500 followers and append the tweet ID to all 500 follower timelines in Redis.
  • Pro: Timeline reads are instant (O(1) lookup from Redis).
  • Con: Huge write amplification if A has 50 million followers (e.g., a celebrity). Generating 50 million Redis writes freezes the queue.

2. Fan-out-on-Read (Pull Model)

  • How it works: When user B opens their app, the system dynamically queries the DB: SELECT tweet_id FROM tweets WHERE user_id IN (following_list) ORDER BY created_at DESC LIMIT 20.
  • Pro: Zero write amplification when a celebrity posts.
  • Con: Slow reads. Running multi-key joins and sorting millions of rows across hundreds of followed accounts kills database latency at scale.

3. The Hybrid Approach (The Expected Senior Answer)

You explain to the interviewer that you use a hybrid threshold:

  • Standard Users (< 25,000 followers): Use Fan-out-on-Write. Push tweets into followers' Redis caches asynchronously via the queue.
  • Celebrities / High-Follower Accounts (> 25,000 followers): Do NOT fan out to followers. Instead, write their tweets only to their personal tweet store.
  • Read Aggregation: When a user opens their timeline:
    1. Fetch their pre-computed Redis timeline (contains tweets from normal friends).
    2. Fetch the latest tweets from the handful of celebrities they follow.
    3. Merge and sort the two lists in memory at the app tier before returning JSON to the client.

How to Deliver This in Under 6 Minutes

  1. Drop the Skeleton: Draw Client -> LB -> Gateway -> Service -> DB and add the Redis cache and Kafka queue.
  2. Define the Write Path: "The user posts a tweet. The Tweet Ingestion Service writes it to the database, then drops a message on Kafka and immediately responds 201 Created to keep user latency under 50ms."
  3. Define the Async Path: "Workers pull the message from Kafka. They fetch the author's followers and push the tweet_id into each follower's Redis timeline list using an LPUSH capped at 800 items."
  4. Define the Read Path: "When a user views their feed, the Timeline Service hits Redis, runs an LRANGE 0 20 to get the latest tweet IDs, hydra-fetches tweet metadata from cache/DB, and returns the feed."
  5. Address the Celebrity Trade-off: Mention the hybrid fan-out model before they even ask. This shows you already know where the template meets its physical limits.

Types & Language Fundamentals

Value types & Ref types

Value Types

  • Storage: Stored on the stack.
  • Assignment: Copies data when assigned.
  • Examples: int, double, char, bool, struct, enum.

Reference Types

  • Storage: Stored on the heap.
  • Assignment: Stores a reference (address) to data instead of copying it.
  • Examples: class, string, interface, array, delegate.

Var, Dynamic, & Object

Type When Used Compile-time Check Runtime Behavior
var When type is obvious Yes (Strongly typed) Fixed type after assignment
dynamic When type is unknown until runtime No Type checked at runtime
object When working with any data type Yes (Boxing/unboxing needed) Can be cast to specific types

Nullable types

Nullable types (?) allow value types to hold null.

Const, readonly, & static

Keyword Behavior
const Must be assigned at compile-time, cannot change.
readonly Assigned at runtime (in constructor), cannot change later.
static Belongs to the class, not instance (shared across all objects).

Tuples vs anon. types

Tuples

A Tuple is a data structure that holds multiple values, often of different types. It’s immutable and can be used for returning multiple values from a method.

Anonymous Types

Similar to Tuples but typically used to hold data in a lightweight, read-only manner, and they are implicitly typed. Anonymous types cannot be returned as methods.

Differences

  • Named fields: Tuples can have named fields, but anonymous types have properties with implicit names.
  • Immutability: Both are immutable, but anonymous types are more often used for single-purpose scenarios (e.g., LINQ queries).

Record vs classes

Record Types are a new reference type introduced in C# 9. They are immutable by default and provide a concise way to define data structures.

Differences from Classes

  • Immutability: Record types are immutable by default. You can create a new instance with modified properties using the with keyword.
  • Value-based equality: Record types compare their values rather than references, while classes use reference equality.
  • Syntax: Compact syntax for property initialization.

== vs .Equals()

  • == (Equality Operator): Compares memory location for reference types, compares values for primitives.
  • .Equals(): Compares actual object values.

Shallow vs Deep Copy

Shallow Copy

Copies the reference of objects within a collection, meaning both the original and the copy refer to the same objects.

Deep Copy

Creates a new instance of the original object and also recursively copies the objects inside it.

  • Manual Copy: You create a new instance and copy properties.
  • Serialization-based: You can serialize the object and then deserialize it to create a deep copy (works well with complex objects).

Extension methods

Extension methods allow you to add new methods to existing classes without modifying their source code.

Defined as static methods inside a static class.

Delegates & Events

  • Delegate: A pointer to a method.
  • Event: A specialized delegate used for notifications.

Reflection

Reflection is the ability of a program to examine and modify its own structure and behavior at runtime.

Common Uses of Reflection

  • Inspecting types and members (properties, methods, etc.).
  • Creating instances of types dynamically.
  • Invoking methods and accessing fields/properties dynamically.

Async/Await

async/await enables asynchronous programming in C#, improving performance by freeing up threads instead of blocking execution.

Key Benefits

  • Non-blocking UI: Keeps user interfaces responsive during I/O operations.
  • High Scalability: Frees thread-pool threads while awaiting external operations in web services.

Lock, Monitor, & Mutex

  • lock: A shorthand for Monitor.Enter and Monitor.Exit. It provides mutual exclusion and is used for protecting critical sections from concurrent access.
  • Monitor: A low-level synchronization primitive for locking and unlocking code. You can also use Monitor.TryEnter to avoid blocking indefinitely.
  • Mutex: A synchronization primitive that can be used across processes, making it suitable for thread synchronization in multi-process environments.

HTTP Fetch

Use the HttpClient class with GetAsync, PostAsync, etc., methods for each HTTP method. Pass StringContent objects for payload data and configure header properties directly on the HttpClient instance.

EF Code/DB First

Entity Framework (EF) is an ORM that maps C# objects to a database.

Approach Description
Code First Write C# classes first, then generate the database schema using Migrations
Database First Start with an existing database, then reverse engineer / scaffold models

Key EF Core Conventions

  • Primary Key: Property named Id or <EntityName>Id inferred as auto-incrementing identity key.
  • Foreign Key: Properties matching <NavigationProperty>Id automatically inferred as foreign keys.
  • Change Tracker: Compares loaded entity snapshots during SaveChangesAsync() to generate targeted SQL updates.
Runtime, Memory & Architecture

What is .NET?

.NET is a framework and runtime developed by Microsoft for building applications. It provides:

  • A Common Language Runtime (CLR) for executing code.
  • A Base Class Library (BCL) for common functionality.
  • Support for multiple languages (C#, VB.NET, F#, etc.).
  • A unified platform to build web, desktop, cloud, mobile, and IoT applications.

.NET, Core, & 5/6/7

Performance Slower Faster Even more optimized
Deployment Installed on Windows Self-contained Self-contained
Support Legacy Modern Latest .NET version
Latest Version 4.8 (No updates) 3.1 (End of life) .NET 7+ (Active)

Cross-platform

.NET Core is cross-platform, supporting Windows, Linux, and macOS. It achieves this through:

  • .NET Runtime (CoreCLR): A platform-agnostic runtime for executing .NET applications.
  • CoreFX Libraries: A set of APIs common across platforms.
  • Portable Libraries: Code libraries that work across different operating systems.

.NET Core uses platform-specific implementations for OS-specific concerns (e.g. file paths), abstracting these details via .NET Standard.

Garbage collection

Garbage Collection (GC) automatically frees memory by removing unused objects from the heap.

GC Process

  1. Mark: Identifies objects that are no longer reachable or in use.
  2. Sweep: Removes unused objects and reclaims memory.
  3. Compact: Reorganizes memory to reduce fragmentation.

Generations in GC

  • Gen 0: Newly allocated objects (frequent collection).
  • Gen 1: Short-lived objects that survived Gen 0.
  • Gen 2: Long-lived objects (e.g., static variables, global instances).

Forcing GC (not recommended): GC.Collect()

Memory & generations in GC

Memory Management: .NET uses a Garbage Collector (GC) to handle memory allocation and deallocation automatically, tracking objects on the managed heap.

Generations

  • Gen 0: Short-lived objects (frequently collected).
  • Gen 1: Objects that survived Gen 0 collection.
  • Gen 2: Long-lived objects (e.g., static variables).
  • LOH (Large Object Heap): Stores large objects (> 85KB), which are collected less frequently to minimize performance overhead.

DI & .NET Core

Dependency Injection (DI) is a design pattern that helps achieve loose coupling by injecting dependencies instead of hardcoding them.

Types of DI

  • Constructor Injection: Most common, dependencies passed into the constructor.
  • Method Injection: Dependencies injected directly into specific methods.
  • Property Injection: Dependencies set via public properties.

Improves testability, maintainability, and follows SOLID principles.

Dependency Injection

Built-in DI Container

.NET Core provides a built-in dependency injection container handling object creation and lifetime management.

Service Lifetimes

  • Transient: Created every time they are requested (lightweight, stateless services).
  • Scoped: Created once per client request (e.g., Entity Framework DbContext).
  • Singleton: Created once on first request and shared across the entire application lifetime.
Frameworks, APIs & Scenarios

Middleware

Middleware is software that sits in the HTTP request pipeline, handling requests and responses before or after they are processed by the application.

Request Pipeline

The request pipeline is a sequence of middleware components. Each middleware can either perform logic, pass the request to the next middleware via next(), or short-circuit and terminate the pipeline.

Minimal APIs

Minimal APIs are architected to create HTTP APIs with minimal dependencies and boilerplate in ASP.NET Core.

  • Introduced in .NET 6 as a lightweight alternative to controller-based APIs.
  • Endpoints defined directly via lambda expressions (e.g., app.MapGet("/", () => "Hello World")).
  • Optimized for microservices and cloud-native applications with faster startup times.

ASP.NET Core Web API (Controller-Based)

Controller-based APIs organize HTTP endpoints into controller classes deriving from ControllerBase.

  • Annotated with [ApiController] and route attributes (e.g., [Route("api/[controller]")]).
  • Provides structured separation of concerns, action filters, automatic model validation, and content negotiation.

ASP.NET Core MVC (Model-View-Controller)

An architectural pattern separating applications into three primary components:

  • Model: Represents application state, data rules, and business logic.
  • View: Renders UI and presentation using Razor syntax (.cshtml).
  • Controller: Handles incoming user requests, manipulates the model, and selects views to render.

Blazor

Blazor is a modern web framework for building interactive client-side web UI using C# instead of JavaScript.

Hosting Models

  • Blazor Server: Component UI runs on the server; UI updates, events, and JavaScript interop are transmitted over real-time SignalR connections.
  • Blazor WebAssembly: Runs directly inside the browser client on top of a WebAssembly-based .NET runtime, providing client-side offline execution.

WCF Protocols

  • HTTP/HTTPS: BasicHttpBinding, WSHttpBinding, WebHttpBinding (Web services, REST, SOAP).
  • TCP: NetTcpBinding (Fast, secure, Windows-only communication).
  • Named Pipes: NetNamedPipeBinding (Same-machine high-performance communication).
  • MSMQ: NetMsmqBinding (Reliable messaging, offline apps).
  • UDP: Custom binding (Lightweight, real-time broadcast updates).
  • WebSockets: NetHttpBinding (Full-duplex, real-time apps).

WPF, Win Forms, UWP

  • WPF (Windows Presentation Foundation): Framework for building rich desktop applications with advanced UI features (2D/3D graphics, hardware acceleration, animations, and data binding with XAML).
  • Windows Forms: Lightweight UI framework for building simple Windows desktop applications. Older than WPF, rapid drag-and-drop design.
  • UWP (Universal Windows Platform): Framework for creating cross-platform apps running across Windows 10/11 devices (PC, tablet, Xbox, HoloLens).
